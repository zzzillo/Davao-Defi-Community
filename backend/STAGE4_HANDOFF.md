# Stage 4: validated image uploads and Cloudflare R2

## Implemented

- `POST /media/uploads?purpose=...` accepts one raw image request body. It does
  not parse a multipart form or issue a presigned URL. The server enforces a
  10 MiB raw-body limit as chunks arrive, then checks that the normalized output
  also fits within 10 MiB.
- Pillow inspects the actual image bytes, accepts one-frame JPEG, PNG, and WebP
  rasters up to 20 megapixels, applies EXIF orientation, and re-encodes a fresh
  pixel-only image. SVG, GIF, animation, truncated or malformed files, MIME
  mismatches, and pixel/byte overages are rejected. EXIF, XMP, and ICC metadata
  are not copied into the normalized object.
- Each object key is generated by the server as
  `media/{purpose}/{uploader_uuid}/{asset_uuid}.{extension}`. The client cannot
  choose a filename or key, replace an existing key, or write directly to R2.
- The S3-compatible R2 adapter is lazy and uses the account endpoint, region
  `auto`, path-style requests, bounded timeouts, and Botocore checksum behavior
  set to `when_required`. It sends no ACL fields. Public URLs use the configured
  HTTPS static domain; missing or malformed storage settings return a generic
  503 on upload while health, authentication, and content routes continue to
  work.
- A `MediaAsset` is recorded as `valid` only in the same transaction as its
  upload audit row, after validation and provider write have succeeded. Private
  assets keep a private owner in JSON metadata; shared assets have no private
  owner. The response does not expose that metadata or the uploader identity.
- Upload authority is checked before reading the body and rechecked under the
  Stage 2 user-mutation lock after decoding. The lock spans the provider write
  and database/audit commit, so a concurrent role demotion or suspension cannot
  complete a now-unauthorized upload.
- New keys can attach only when a registered asset is `valid`, has the exact
  purpose, and has the right private owner. This check covers profile photos,
  blog covers, event banners, recap gallery images, and partner logos on create
  and update. Existing keys may remain unchanged during edits. Existing
  external HTTP(S) event banner URLs are still accepted. Resource deletion does
  not delete a file that may be referenced elsewhere.
- `/users/me` and the admin profile endpoint accept a validated
  `profile_photo_key`. Admins may upload a profile photo for a target allowed
  by the Stage 2 profile rules; the asset's uploader remains the acting admin.
  Authenticated user responses include the resolved `profile_photo_url`.

### Purpose and role scope

| Purpose | Upload scope |
| --- | --- |
| `profile_photo` | Every active user may upload for themselves. Admins may target an allowed member, official, or peer admin profile; superadmins may target any profile. |
| `blog_cover` | Every active user may upload for their own blog. Only a superadmin may upload for another blog owner. |
| `event_banner`, `recap_image`, `partner_logo` | Officials, admins, and superadmins upload shared assets. Any official-tier writer may attach a valid shared asset. |

## API contract

Send the file bytes directly as the request body. The `Content-Type` header must
match the decoded bytes and be `image/jpeg`, `image/png`, or `image/webp`.

```http
POST /media/uploads?purpose=blog_cover
Authorization: Bearer <Clerk session token>
Content-Type: image/webp

<raw image bytes>
```

`owner_user_id` is an optional UUID query parameter for a permitted upload on
behalf of a profile or blog owner. Shared purposes reject it. A successful
response is HTTP 201 and contains `id`, `storage_key`, `purpose`, `public_url`,
`content_type`, `byte_size`, `width`, `height`, and `validation_status`. Upload
validation failures return 4xx; absent or unavailable storage returns 503 with
a generic reason and no provider exception text.

The frontend should POST the file to the backend using its authenticated API
client, pass the purpose, and use the returned `storage_key` in the content or
profile write. A browser-to-R2 request is not used, so no R2 bucket CORS rule is
needed. The frontend's prior presigned-upload stub should be adapted in Stage 5
to this raw-body contract; Stage 4 does not change frontend files.

## Cloudflare R2 setup

R2 is configured in the ignored `backend/.env`: the user created the standard
`ddc-media` bucket, enabled its Public Development URL, and supplied the S3
Access Key ID, Secret Access Key, and account ID. The file is mode 600. A
generic Cloudflare API token supplied separately was not stored or used; this
adapter uses only the bucket-scoped S3 credentials.

For future setup or credential rotation, follow these Cloudflare steps:

1. In the [Cloudflare Dashboard](https://dash.cloudflare.com/), open **Storage
   & databases → R2** and create a standard, non-jurisdiction-restricted
   development bucket (the current bucket is `ddc-media`).
2. In **Manage API Tokens**, create an Account API token or User API token with
   **Object Read & Write** permission and apply it to that bucket only. Copy
   the S3 Access Key ID and Secret Access Key once; Cloudflare does not show the
   secret again. The application token does not need bucket-create permission.
3. Copy the account ID from the R2 Overview page or token confirmation. The
   adapter uses `https://<ACCOUNT_ID>.r2.cloudflarestorage.com` and region
   `auto`, as in Cloudflare's [S3 API setup](https://developers.cloudflare.com/r2/get-started/s3/).
   This code targets the standard endpoint; do not select a jurisdiction-
   restricted bucket for this configuration.
4. In the development bucket's settings, enable its **Public Development URL**
   and copy the HTTPS URL shown there. This URL is rate-limited and suitable
   only for development. Use a Cloudflare custom domain for production.

Put the following values only in the ignored `backend/.env` file. Leave
`backend/.env.example` as a blank template, keep the file mode private, and do
not paste keys into chat or source control:

```dotenv
STORAGE_PUBLIC_BASE_URL=https://<public-development-domain>
R2_ACCOUNT_ID=<cloudflare-account-id>
R2_BUCKET_NAME=ddc-media
R2_ACCESS_KEY_ID=<bucket-scoped-access-key-id>
R2_SECRET_ACCESS_KEY=<bucket-scoped-secret-access-key>
```

`STORAGE_PUBLIC_BASE_URL` must be an HTTPS origin with an optional simple path
prefix, without credentials, query, fragment, or traversal segments. Restart
the backend after editing `.env` to reload cached settings. Verify with a
authenticated development upload only after the bucket, token, account ID, and
public URL are ready. R2 CORS is unnecessary for this server-mediated flow.

The connection was tested with one generated 3×2 PNG at a unique setup-check
key. The real adapter uploaded normalized bytes; the Public Development URL
returned HTTP 200 with matching content type and SHA-256. The adapter deleted
only that key, and S3 `HEAD` returned 404. The parent also verified that the
bucket responded to `HEAD` and the setup-check prefix was empty. This diagnostic
created no `MediaAsset`, audit row, or application content, and used no user
image.

## Failure and cleanup behavior

- A provider write failure triggers a best-effort delete of the newly generated
  key in case the request reached R2 before the network error was returned.
- A database flush or audit failure rolls back the metadata and audit row, then
  attempts to delete only that request's newly generated object.
- If the database commit acknowledgement is lost, the object is retained
  because the `MediaAsset` and audit transaction may already have committed.
  The API returns `media_commit_uncertain`; confirm the database and bucket
  state before retrying to avoid duplicate uploads. There is no automatic
  cleanup job or broad object-delete endpoint.
- No migration is required. `media_assets`, its `validated_at` column, and the
  activity audience/owner fields were added in prior stages; Stage 4 uses those
  existing columns. `ActivityResource.MEDIA` is a code-level string value.
